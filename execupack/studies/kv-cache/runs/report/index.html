ExecuPack · ExecuTorch 1.5.1 Android runtime · Snapdragon SM8975 reference phone · 2026-11-21

KV cache precision on a phone: CPU and GPU

Four small models, 2k / 8k / 32k windows, the same 4-bit GPTQ weights in every file of a pair. On the CPU each pair differs only in how the KV cache is stored; on the GPU the fp16 file also computes in fp16.

Findings

CPU: turn the int8 cache on for the 8k and 32k windows; at 2k it is optional. On this phone it cut the time per generated token 1.7–3.8× at 7.9k tokens into a chat and 2.5–3.3× at 32.5k (17× for Qwen3-1.7B, whose fp32-cache file was near the phone's memory limit), and cut peak memory by up to 4.9 GiB. It is a real perturbation of the output: measured directly, the int8 file's next-token distribution differs from the fp32-cache file's by KL 0.013–0.037 on average (coarsened to the reference's top 64 tokens), and the top token differs on 6–15% of positions (for scale, that KL is 5–23% of each fp32-cache file's own divergence from the fp32 model; the two are not additive). Its effect on divergence from the fp32 model showed no consistent direction: each cell's mean moved by −0.020 to +0.028, the 144 paired needle questions with valid state (LFM excluded) split 7 found only with int8 and 4 only with fp32, and on the app questions the averages improved while some individual prompts got worse. Treat this as a provisional recommendation: the intervals reflect the sampled 128-token spans of three books (one at 32k for some cells), with no preset loss margin, so they do not establish equivalence. Confirm through the app's own runner, at long contexts, before shipping.

GPU: keep the fp32 files. The int8 cache cannot be used, and fp16, faster and smaller up to 8k, broke down in Llama's 32k file. In ExecuTorch 1.5.1 the int8 cache does not export for Vulkan, and Gemma 3 and LFM2.5 do not run on Vulkan in this recipe. Vulkan's fp16 mode (force_fp16: floating-point tensors inside the Vulkan delegate, the KV cache among them, kept in fp16; the quantized weights unchanged) was measured on Llama-3.2-1B at 2k, 8k and 32k and on Qwen3-1.7B at 2k and 8k. Up to 7.9k tokens it behaved: at 1.9k tokens, with the GPU uncapped, it decoded 1.18–1.21× faster on Llama and 1.05× (2k file) to 1.29× (8k file) on Qwen, and it used 0.4–2.4 GiB less GPU driver memory (Llama 8k: 5.6 → 3.2 GiB). The two files' outputs differed by a mean coarsened KL of 0.0012–0.0067, below the CPU int8 cache's in every matching cell. Against the fp32 model no change was detected on Qwen at either window or on Llama at 2k; Llama 8k's mean divergence rose by about 0.012 at both depths, in all three books (perplexity moved slightly both ways, and one needle of 21 was lost), and Llama's 32k file rose by 0.003 at 1.9k on its single book. At 32.5k tokens Llama's fp16 file failed: its divergence from the fp32 model was 1.85 against fp32's 0.26, it agreed with that model's top token on 28% of positions against 62%, and it answered none of the 9 needles to fp32's 9. That is one model and one book (Qwen has no 32k GPU file), but the failure is not subtle, and a second run reproduced it exactly. Where between 7.9k and 32.5k it begins was not measured, and the cause is not established (a candidate is below). ExecuPack's published GPU files are fp32; on this evidence they should stay so, and fp16 would need checking at each window's full depth before any use. Separately, ExecuPack's published Llama-3.2-1B GPU files at 16k and 32k did not load on this phone (an abort during loading, through the 1.5.1 Vulkan library's Module API; the app's own runner was not tested); the study's 32k file, built the same way but with a 256-token prefill chunk, loaded and ran. Sustained GPU work throttles this phone within 10–20 seconds when a run starts near 50 °C and within one to two minutes from 30–40 °C, and throttling moves speed far more than the cache does.

What was measured

  • Files. Llama-3.2-1B-Instruct, LFM2.5-1.2B-Instruct, Qwen3-1.7B and Gemma-3-1B-it, each exported with ExecuPack's recipe (4-bit GPTQ weights in groups of 32, int8 dynamic activations, int8 embeddings) at 2k, 8k and 32k windows. One GPTQ solve per model. On the CPU the two files of a pair differ only in the cache; on the GPU, fp16 also changes the precision of the floating-point computation (below). CPU files use XNNPACK; GPU files use Vulkan.
  • Phones. Three Snapdragon SM8975 reference phones (Android 17, 8 cores, 11.5 GB) in Qualcomm Device Cloud. The CPU pass ran on the first; the CPU re-run at 2k and 8k and most of the GPU pass on the second; the GPU runs the second did not finish (Llama at 32k, Qwen at 8k, Qwen's app questions) on the third. Both files of every pair ran on the same phone. Where two phones ran the same file, the quality values matched exactly; speeds matched for the GPU Llama 2k pair (within 0.3%) but differed by up to about 30% on the CPU (Qwen at 2k), so speed comparisons across phones are rough. CPU files ran on the executorch-android 1.5.1 library with 7 threads, as the app does; GPU files on executorch-android-vulkan 1.5.1, because the plain library has no Vulkan backend.
  • Long text. Three PG-19 test-set books (10321, 10356, 10762), 32,500 tokens each inside the model's chat template, with nine RULER-style needles. At 1.9k, 7.9k and 32.5k tokens the phone scores 128 teacher-forced next-token predictions against the fp32 Hugging Face model. Llama and Qwen at 32k on CPU ran one book (time), and so did Llama at 32k on the GPU; Qwen has no 32k GPU file (below).
  • Short chats. The 141 held-out app questions from the earlier GPTQ/AWQ experiments: first-token divergence under the app prompt, and divergence along the fp32 model's replies (every third question, 47 replies).

CPU (XNNPACK): fp32 against int8 cache

Every model, window and depth, fp32-cache file against int8-cache file. The int8 cache is ExecuTorch's quantize_kv_cache: keys and values stored as int8 with a scale and zero point per token and head, attention computed by its int8 kernel (which also rounds the query to int8).

Decode speed against depth

Each generated token reads the whole cache, so a cache a quarter the size pays off more the longer the chat. At 1.9k tokens the gain ranges from none (LFM2.5's 32k file, which attends in only 6 of its 16 layers) to 2.8× (Qwen); at 7.9k it is 1.7–3.8×; at 32.5k, 2.5–3.3×, and 17× for Qwen, whose fp32-cache file peaked at 8.2 GiB resident on an 11.5 GB phone (memory pressure is the likely cause; the harness did not record swap or reclaim). Prefill changes less. The columns group whole chunks by the position they start at, and the first group includes each file's first call after loading, so read them as rough.

The window itself costs speed

At the same 1.9k tokens, a file exported with a larger window usually decodes slower: with the fp32 cache, Llama 40 tok/s in the 2k file against 25–26 in the 8k and 32k files, LFM 66 against 38–40, Gemma 48 against 35–36. Qwen is the exception with the int8 cache (27, 30, 36 tok/s). At the same positions the files' outputs are identical across windows, so the window costs speed and memory, not quality. The smallest window that covers a use case matters as much as the cache type.

Quality

Each point is the change in mean divergence from the fp32 Hugging Face model when the int8 cache replaces the fp32 cache: KL(HF ‖ int8 file) minus KL(HF ‖ fp32 file), paired position by position, with a block bootstrap (16 neighbouring positions per block). It is not the divergence between the two files' outputs, and opposite movements can cancel; the direct comparison is in the re-run section below, and it is larger (KL 0.013–0.037). The absolute divergence (0.15–0.33) comes from the quantized model; the cache moves it by hundredths. The largest increase is Llama at 32.5k, measured on a single book and so descriptive only (+0.028, perplexity 45.7 → 48.5, agreement with the fp32 model's top token 63% → 60%); there the int8 cache found all 9 needles to the fp32 cache's 7. The intervals resample 16-position blocks within the sampled spans, not whole books, so they describe these spans rather than PG-19 at large.

Excluding LFM (below), the two caches gave the same outcome on 133 of 144 paired needle questions; 7 were found only with int8, 4 only with fp32. Both caches fail many of the same long-range needles: Gemma finds 4–5 of 27 at 32k and Qwen 4–5 of 9, where the fp32 Hugging Face model finds 12 and 7; this study does not isolate why. LFM's needles here were answered after rewinding the cache, which does not restore LFM2's convolution state, so its rows are left out of the totals; the re-run below answered its 2k and 8k needles from a fresh model and full prefix and got exactly the same outcomes (12 of 12, 21 of 21, both caches), so the rewind did not change them there (its 32k row was not re-run).

On the app questions, the average first-token divergence fell for every model (significantly for Llama, LFM and Qwen), but not every prompt improved: rows that got worse by more than 0.1 KL were 0 for Llama, 9 for LFM, 18 for Qwen and 44 for Gemma (against 67, 23, 23 and 54 that improved). Qwen agreed with the fp32 model's first token on 120 of 141 questions with the int8 cache against 124 with fp32, and its worst question went from 4.5 to 13.4 KL. Along the fp32 replies no model moved significantly. An earlier x86 run with a different Qwen solve had shown int8 +0.82 worse on this held-out metric; it is dominated by a few uncertain questions and is not a stable signal in either direction.

GPU (Vulkan): fp32 against fp16 cache

The plain executorch-android 1.5.1 library has no Vulkan backend (Backend VulkanBackend is not registered); executorch-android-vulkan 1.5.1 has, with the same Java API, and runs these files. What could be built and run:

  • int8 cache: does not export for Vulkan. Vulkan has no quantized attention, and lowering the int8 cache's per-token quantization fails on a data-dependent shape check (GuardOnDataDependentSymNode in FuseBatchNormPass).
  • fp16: Vulkan's force_fp16 stores and computes the delegate's floating-point tensors in fp16, the KV cache included; the 4-bit and 8-bit quantized weights stay as they are. It is the only reduced-precision cache on the GPU in 1.5.1, so the GPU pair is fp32 against fp16, and unlike the CPU pair it changes the precision of the floating-point computation as well as the cache.
  • Models: Gemma 3 failed in this export recipe: its sliding-window attention crashes the Vulkan partitioner (IndexError in find_causal_sdpa_patterns). LFM2.5 was not attempted: the pipeline excludes it from Vulkan (no kernel for its short convolution, found under ExecuTorch 1.4.0).
  • 32k: Llama's 32k files built with the pipeline's 2,048-token prefill chunk did not run: the fp32 one exited with status 134 (an abort) on its only attempt on the second phone, with no system log captured; the fp16 one was not run. ExecuPack's published Llama 16k and 32k GPU files, built the same way, abort the same way on the third phone, where the log was kept: an exception thrown while loading, whose message was lost (section below). Vulkan's attention allocates two temporaries of heads × prefill chunk × window (below), large at these windows with a 2,048-token chunk (2 × 4 GiB at 16k, 2 × 8 GiB at 32k, in fp32), so a size or device limit is the likely reason. The log does not name it; the abort comes about 10 ms after the Vulkan device is created, before the weights could have been uploaded, which points to a limit check rather than running out of memory; and Vulkan caps the prefill dimension of buffer-backed attention allocations that would exceed its buffer limit, so this arithmetic need not be what is actually allocated. Rebuilt with a 256-token prefill chunk, and otherwise identical, both of Llama's 32k files loaded and ran on the third phone. Qwen's 32k fp32 export ended with status −9 on the 52 GB build machine, most likely the kernel's out-of-memory killer, though no record of it was kept, so Qwen has no 32k GPU file.
  • 4-bit cache: not available on any backend in ExecuTorch 1.5.1.

Heat. The GPU throttles quickly. In Llama's 8k runs its thermal cap went from level 0 (1,450 MHz) to level 12 (636 MHz) between about 10 and 20 seconds after the start, admitted near 50 °C. From a cooler start it takes longer: Llama's 32k runs admitted at 30–40 °C first throttled after about 60–100 seconds, the one admitted at 48 °C after about 17. Started right after 90 minutes of CPU runs (GPU at level 12, device thermal status severe), Llama's 2k files decoded at 16.7 and 30.5 tok/s instead of 47 and 57. Those runs are kept aside and not used.

The runs reported here were admitted by a gate: it waited, for up to 30 minutes, until the cap was lifted, the device thermal status was at most 1 and, from the Qwen 2k books on, the GPU was at or below 50 °C. That last condition was added after one Qwen book, admitted at level 0 while still hot, reached level 8 during its run. On the second phone the session monitor saw no run admitted on timeout, but the gate's own log stayed on the phone, so those starting temperatures are not in the retained record; the third phone's log was kept, and every one of its stream runs was admitted by the conditions, none on timeout, at 30–49 °C (app-question runs were not gated, on either phone). The gate does not make runs start equally cool: it admits at the first reading of 50 °C or less, which after a run came within one to two minutes at about 49 °C, while the session's first run started at 30 °C and the GPU read 38 °C after 16 idle minutes. Every book of Qwen 2k and 8k, Llama 8k and Llama 32k ran as its own process. Llama's 2k files, run before that change, kept three books in one process each and stayed at level 0 throughout. A sampler recorded the cap every 2–5 seconds, and the table labels each decode with the cap estimated for it: its decode window is reconstructed from step times, so the labels are approximate.

Measured: Llama-3.2-1B at 2k and 8k and Qwen3-1.7B at 2k on the second phone, three books each, both caches, plus Llama's app questions; Llama at 32k (one book) and Qwen at 8k (three books) and Qwen's app questions on the third, both caches each. The first phone's Llama 2k pair (47.0 and 57.1 tok/s) reproduced on the second within 0.3%; the third phone reproduced the second's Qwen fp16 app run exactly (section below).

Decode speed against depth

From an uncapped start, at 1.9k tokens, fp16 decoded faster than fp32 by 1.21× in Llama's 2k file, 1.19× in its 8k file and 1.18× in its 32k file, and by 1.05× in Qwen's 2k file and 1.29× in its 8k file. In Llama's 32k file the 7.9k checkpoint also came before any throttling (its 256-token chunks reach 7.9k in 9–14 seconds; estimated level 0 for both files), and there fp16 was 1.29× faster. Every deeper measurement was throttled. At 7.9k in the 8k files, after 11–32 seconds of prefill, fp32 ran at an estimated level 11–12 and fp16, which does less work, at 5–12, so fp16's 1.36× (Llama) and 1.66× (Qwen) include running cooler: closer to what sustained use looks like, but not a same-clock comparison. At 32.5k both of Llama's 32k files ran at level 12, after 2.7 (fp16) and 3.7 (fp32) minutes of prefill, and decoded at 6.6 and 5.3 tok/s. The prefill columns start uncapped and gained 1.09× (Qwen 2k) to 1.58× (Qwen 8k) over the first 2k tokens; later columns ran while the GPU throttled and are confounded the same way. Llama's 32k row comes from the first pair, whose fp32 run started 18 °C cooler; the repeat gave 1.72× and 2.06× for the 8–16k and 16–32k columns, against the row's 1.23× and 1.35×. None of this measures steady-state throughput: the runs were short and separated by cooling. Over the whole 32k prefill, fp16 was 1.35× faster in the first pair and 1.97× in a repeat where both runs started at 38–40 °C (the first pair's fp32 run had started 18 °C cooler; section below); a long GPU prefill's speed depends heavily on how warm the phone is when it starts.

The window and the prefill chunk also change decode speed, unlike on the CPU: at the same 1.9k depth Llama decoded at 47.1 tok/s (fp32) in its 2k file, 57.2 in its 8k file and 66.2 in its 32k file (a 256-token chunk, third phone), and Qwen at 28.7 in its 2k file and 36.7 in its 8k file (third phone). This was not investigated, and the 32k and Qwen 8k rows come from the third phone, so phone-to-phone differences (up to about 30% on the CPU) may account for part of it. The decode chart's panels, each model's largest window, both come from the third phone. Against the CPU on the same phone, Llama's 2k fp32 file decoded at 47.1 tok/s on the GPU and 41.6 on the CPU; fp16 on the GPU (57.0) about matched the int8 cache on the CPU (57.8). At 32.5k, throttled, the GPU fp32 file (5.3 tok/s) matched the CPU int8 cache (5.3) and was 3.4× the CPU fp32 cache (1.6), on different phones.

Memory

GPU files keep their buffers in the GPU driver's memory, which is not in a process's resident memory; the table adds the Adreno driver's per-process peak (/sys/class/kgsl/kgsl/proc/<pid>/kernel_max). With fp32, Llama needs 2.4 GiB of it at 2k and 5.6 GiB at 8k, far more than its cache (128 and 512 MiB). ExecuTorch 1.5.1's Vulkan attention (backends/vulkan/runtime/graph/ops/impl/SDPA.cpp) allocates two temporary buffers of heads × prefill chunk × window, the attention weights and their softmax. That fits the 3.3 GiB growth from 2k to 8k, about 1.5 GiB per buffer plus the larger cache, and it fits the 32k file: with a 256-token chunk its two buffers are half the 8k file's while its cache is 2 GiB, and it peaked at 4.9 GiB, below the 8k file's 5.6. The full allocation was not itemised. fp16 halves those buffers along with the cache: Llama 1.7, 3.2 and 2.8 GiB at 2k, 8k and 32k; Qwen 2.4 → 1.9 GiB at 2k and 5.2 → 3.1 GiB at 8k. Resident memory on the CPU side stays near 0.5 GiB for every file. For a GPU file the prefill chunk is a memory setting as well as a speed one.

Quality

Directly, KL(fp32 file ‖ fp16 file) averaged 0.0012–0.0067 at every point up to 7.9k tokens: 0.0013 on Llama 2k, 0.0031 and 0.0067 on Llama 8k at 1.9k and 7.9k, 0.0012 and 0.0039 on Llama 32k, 0.0029 on Qwen 2k, and 0.0035 and 0.0030 on Qwen 8k. Its worst single positions were 0.01–0.18. In Llama's files it grows with depth (32k file 0.0012 → 0.0039, 8k file 0.0031 → 0.0067), while Qwen's 8k file stays flat (0.0035, 0.0030). As on the CPU it is coarsened: the files are compared on the Hugging Face model's top 64 tokens plus one bucket for the rest. That bucket holds 10% (Qwen) to 35% (Llama's 32k file at 1.9k) of the probability on average, so differences inside it are not seen, and the coarsened KL is a lower bound on the full one.

Against the fp32 Hugging Face model, up to 7.9k tokens: no change was detected on Llama 2k (−0.0004, interval −0.0046 to +0.0031), Qwen 2k (+0.0034, −0.0004 to +0.0073) or Qwen 8k (−0.0044 and −0.0009 at 1.9k and 7.9k, both intervals including zero). On Llama 8k, fp16's mean divergence was higher in all three books at both depths: +0.013 at 1.9k and +0.012 at 7.9k, and the block-bootstrap intervals exclude zero. With three books this describes these texts rather than estimating a population effect, and one book supplies most of the 1.9k increase. Perplexity moved a little in both directions (47.0 → 47.9 at 1.9k, 40.7 → 40.5 at 7.9k), and one needle of 21 was lost (20 against 19), none gained. Llama's 32k file, one book, rose by +0.003 at 1.9k (interval +0.0006 to +0.0051, which excludes zero; descriptive, as a single book) and +0.005 at 7.9k (interval includes zero). Vulkan's numerics also vary with the window: at the same 1.9k depth, Llama's 8k fp32 file diverged less from the reference than its 2k file (0.219 against 0.226), which the CPU files never did. Llama 2k, Qwen 2k and Qwen 8k found every needle with both caches.

At 32.5k tokens, Llama's fp16 file broke down. Its mean divergence from the fp32 model was 1.853 against fp32's 0.261 (the CPU files on the same book: 0.293 fp32, 0.321 int8), its perplexity 254 against 44, its agreement with that model's top token 28% against 62%, and the two GPU files' outputs differed by a mean coarsened KL of 1.37 (worst position 8.0). fp16's divergence was higher at 127 of the 128 scored positions, and the two files' outputs differed by at least 0.11 at every one: not a few outliers. fp16 also put 59% of its probability outside the reference's top 64 tokens, against fp32's 24%, so the coarsened KL of 1.37 understates the difference. It answered none of the 9 needles, all asked at the end of the 32.5k-token text, each time repeating part of the question ("the special magic number for …"), where fp32 answered all 9 (the fp32 Hugging Face model 8). It is one book, but the effect is two orders of magnitude beyond anything else in the GPU pass. A second run of the same file, started from a cooler GPU (below), gave identical values at every scored position: the failure is deterministic, not noise. Where between 7.9k (where fp16 was still close to fp32) and 32.5k it begins was not measured. The cause is not established. One candidate, in the source: ExecuTorch 1.5.1's Vulkan attention for LLMs sums over every attended position twice, for the softmax's denominator (sdpa_attn_weights_softmax.glsl) and for the attention-weighted sum of values (sdpa_compute_out_*.glsl), each in the tensor's own type. For fp16 tensors stored as buffers that type is fp16; for textures it is a float type, but the all-fp16 shader variants are compiled at medium precision, which lets the driver compute in fp16 anyway. Rounding error in such sums grows with the number of positions. Which storage the 32k file's attention tensors use was not checked, and this was not isolated.

On the app questions (2k files): Llama's first-token divergence averaged 0.234 with fp32 and 0.209 with fp16 (−0.026, interval −0.056 to +0.002); 12 rows got worse by more than 0.1 and 20 better; the largest increase took one row from 0.22 to 0.63; along the replies it barely moved (0.085 and 0.083). Qwen's, both runs on the third phone, averaged 1.105 with fp32 and 0.519 with fp16 (−0.587, interval −0.947 to −0.290), with 8 rows worse and 30 better (the largest increase 3.5 → 7.8), and along the replies 0.281 and 0.255 (−0.027, interval −0.049 to −0.005). Both intervals lie below zero: on these short prompts Qwen's fp16 file stayed closer to the fp32 model than its fp32 file did. The held-out average is dominated by a few uncertain questions (medians 0.003 and 0.002; fp32's five largest rows are 8–20), as with the CPU int8 cache, so this is a measured difference on these 141 questions, not evidence that fp16 is more accurate in general, and it says nothing about long contexts, where Llama's fp16 file failed.

GPU checks on a third phone

The third phone (QDC device unit-a4448d, SM8975) ran what the second did not finish. Qwen's four GPU files were rebuilt from the same codes and tree, and all four matched the second phone's copies byte for byte (sha256). Llama's two 32k files with a 256-token chunk were built once, after the second phone's session ended, and never ran there; only their transfer was hash-checked, so the fp16 failure rests on one build, one phone and one book (and one repeat of the run). Three checks ran alongside. The 32k pair in reverse order. The first 32k fp16 run started at a GPU temperature of 48 °C against fp32's 30 °C, and a 32k run throttles within its first minute or two, so the pair was repeated with fp16 first and each run admitted only at or below 40 °C. Started at 38 °C (fp16) and 40 °C (fp32), the repeat reproduced every quality value of the first pair exactly and its decode speeds within 0.6% (the 1.9k and 7.9k checkpoints ran uncapped and the 32.5k one at level 12 in all four runs); the whole 32k prefill took 129 seconds with fp16 against 253 with fp32 (1.96×), where the first pair, fp32 starting 18 °C cooler, gave 163 against 220 (1.35×). Reproduction across phones. Qwen's fp16 app run gave the same value on every one of the 141 held-out questions on the third phone as on the second, and its replies matched too; the page pairs the two third-phone runs, and the numbers would be the same with the second phone's fp16 run. ExecuPack's published files. The Llama-3.2-1B Vulkan files published on Hugging Face at 16k and 32k are built like the 32k file that aborted on the second phone (ExecuTorch 1.5.1, 2,048-token prefill chunk; their export reports count the cache but not Vulkan's attention temporaries, and mark them as fitting a 5 GB budget). Each was fetched from the Hub (sha256 checked against its LFS record) and loaded once through the study harness. Both aborted (exit status 134) inside Module.loadMethod, about 10 ms after the Vulkan device was created: a C++ exception was thrown while loading (the frame in the ExecuTorch library is not symbolised) and the Java binding could not translate it (fbjni's assertion ptr), so the exception's own message was not logged. A file with the same recipe and a 256-token chunk loads and runs at 32k (above), and the study's 8k file with a 2,048-token chunk loaded on the second phone, which is consistent with the attention temporaries (heads × chunk × window) exceeding a device or Vulkan limit; the exact limit was not identified. Through this library's Module API (file memory-mapped) on this phone, then, ExecuPack's published Llama-3.2-1B GPU files at 16k and 32k do not load. Independent review

OpenAI Codex reviewed the CPU study read-only: the harness, the reference, the statistics and every claim in an earlier draft of this page. It found no off-by-one in the teacher forcing and judged that draft's verdict unsupported. This version addresses each point:

  • The KL claim. The draft said the int8 cache changes the output distribution by at most 0.03 KL. What was measured is the change in each file's divergence from the fp32 model, which does not bound the divergence between the two files. Now worded as such; a CPU re-run on a second phone recorded the per-position log-probabilities a direct comparison needs, and the page now reports that comparison (KL 0.013–0.037).
  • LFM needles. Rewinding the cache does not restore LFM2's convolution state. Re-run from a fresh model and full prefix at 2k and 8k: same outcomes; the 32k row stays out of the totals.
  • Intervals. Single-position bootstrap over correlated positions was too narrow. Now block bootstrap (books), by reply (replies) and by question (held-out); single-book cells marked as descriptive; no claim of equivalence.
  • Overstated wording. The draft said the int8 cache was never worse on the app questions, called Gemma's needle successes misses, attributed the misses to the 4-bit weights, gave inaccurate speed ranges, and called Qwen at 32k usable despite a 15-minute prefill. All corrected; per-prompt regressions and paired needle outcomes are now reported.
  • Units and charts. Memory in MiB; the speed chart's axis follows the data; prefill columns labelled by chunk start.

Not addressed, by design or time: repeated timing runs, temperature control on the CPU, and validation through the app's own runner at long contexts.

Third review. Codex recomputed the CPU re-run and the GPU pass from the raw results. It reproduced every GPU speed and ratio, the memory savings, the direct KL values and the needle and app aggregates, and confirmed the KL's direction and the per-book merges. It found:

  • quality wording too categorical ("no drift", "unchanged", "quality cost")
  • the thermal gate's guarantees overstated: it admits a run after a timeout, and its log stayed on the phone
  • the thermal labels presented as exact
  • the later-chunk prefill gain shown as uncapped
  • the 32k memory projection wrong (about 18.7 GiB, not 16) and the abort over-attributed
  • the top-token range misstated (6–15%, not 8–11%)
  • a second cross-phone speed exception (LFM at 2k)
  • a few smaller errors

All are corrected above. The gate now treats a missing reading as hot and logs any admission on timeout.

Fourth review (the third phone). Codex could not run this round: the ChatGPT account it is signed in with rejected every model. The same brief went to an independent Claude agent, read-only, which recomputed the round's numbers from the raw results. It confirmed every headline number (the 32k breakdown, speeds, memory, direct KL, needles, app questions, the repeat's exact reproduction and the admission temperatures) and found:

  • a false provenance claim: only Qwen's four files were rebuilt and matched; the Llama 32k pair was built once and never ran on the second phone
  • an inconsistent abort explanation: the 16k file's temporaries would fit in memory, the abort comes about 10 ms (not 0.1 s) after the device is created, and Vulkan's cap on buffer allocations had been dropped from the text
  • an inaccurate account of the candidate shader cause: the maximum is exact in any precision, the accumulator type depends on storage, and the attention-times-values sum was missing
  • over-general wording: "fp16 broke down at 32k" (one model), "throttles within about 20 seconds" (only from about 50 °C), needles that "moved both ways" (one was lost), "each phone reproduced the previous one" (quality did; CPU speeds did not)
  • phone labels missing from the quality, needle and app tables, and the 32k prefill columns taken from the mismatched first pair without comment
  • small rounding errors (1.97×, 3.4×, 30.5 tok/s) and stale code comments

All are corrected above. A Codex pass on this version is still to be done.

Method

  • Harness. StudyBench calls the program's forward() through the Android library's Module API: prefill in chunks of get_max_seq_len − 1 tokens (2,047; 511 for Gemma; 255 for the GPU 32k files), then single-token decode steps whose input is always the book's true next token. Each forward() is timed, including tensor creation and copying the logits out, not the scoring that follows. Model files reached the phone with sha256 checks.
  • Divergence. KL(fp32 HF ‖ file) over the reference's top 64 tokens plus one bucket for the rest, as in the earlier experiments. The GPU pass also stored each file's log-probabilities on those 64 tokens, so its two files can be compared directly.
  • Intervals. Block bootstrap over runs of 16 neighbouring positions for the books; by reply for the replies; by question for the held-out first tokens. 95% percentile intervals, no correction for the number of comparisons; single-book cells are descriptive.
  • References. The book reference is Hugging Face fp32 on a GPU with TF32 off, on the same token IDs and model revisions as the exports. The app reference is Hugging Face fp32 on the CPU (the earlier experiments' awq_compare reference; Gemma's made the same way for this study).
  • Gemma 3. ExecuTorch 1.5.1 has no CPU path for it; this study adds one (separate RoPE for the sliding layers, ring caches, 512-token prefill chunks). The ExecuTorch model matched Hugging Face at KL ~1e-9 before quantization, and the exported 2k file without quantized linears at KL 0.0003.

Notes and limits

fp16 on the CPU and 4-bit caches. A 16-bit cache on the CPU needs an fp16 model, and the 1.5.1 Android library has no XNNPACK kernel for 4-bit weights with fp16 activations: every CPU fp16 file failed to load (xnn_status_unsupported_hardware), though fp16 itself runs on this phone. ExecuTorch 1.5.1 has no 4-bit KV cache on any backend.

Speed. No repeated runs of the same file; runs of a pair were not adjacent in time and started at different temperatures (logged, not controlled); downloads overlapped some CPU runs, notably LFM's 32k int8 run. The harness's fp32 decode on Qwen 2k was close to the app's own runner (14.1 vs 15.9 tok/s, different prompt and warm-up); with int8 the runner was faster (36.6 vs 27.0). The CPU runs were not gated on temperature on either phone. The second phone reproduced the first's CPU decode speeds within about 5% (LFM and Qwen at 2k aside), which shows the runs repeat but cannot rule out a bias both shared. The GPU runs were gated and labelled (see the GPU section), because there the effect was threefold; the gate set an upper bound on the starting temperature, not an equal one, which the 32k repeat addresses for that pair only. Absolute CPU speeds are approximate, and the ratios carry the same run-order and temperature caveats; the large effects (2–4× at depth) are well beyond them, the small ones (under ~1.15×) are not.

Scope. Three phones of one model, three books (one at 32k for some cells, including the GPU's only 32k result), teacher-forced spans of 128 tokens and short needle answers. This measures how the cache changes the model's predictions, not end-to-end chat quality.

Before shipping the int8 cache. sizing.kv_bytes_per_token must count it (1 byte per value plus a scale and zero point per token and head, about 27% of fp32) for fits_phone_budget and the README; no work path may contain "int8", which ExecuTorch 1.5.1 mistakes for an int8 weight-only checkpoint; and the cache stays off GPU builds.

For the GPU builds. Keep them fp32. Llama's published 16k and 32k GPU files do not load on this phone through the 1.5.1 Vulkan library; a 256-token prefill chunk made a 32k file load, run and match the CPU files' quality (divergence from the fp32 model 0.26 against the CPU's 0.29 and 0.32 at 32.5k on the same book). Before changing the chunk for the published files, check the other models and windows, and that sizing counts Vulkan's attention temporaries, which its estimate of 3.6 GB for the 32k file leaves out.
