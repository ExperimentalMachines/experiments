Findings

CPU: turn the int8 cache on for the 8k and 32k windows; at 2k it is optional. On this phone it cut the time per generated token 1.7–3.8× at 7.9k tokens into a chat and 2.5–3.3× at 32.5k (17× for Qwen3-1.7B, whose fp32-cache file was near the phone's memory limit), and cut peak memory by up to 4.9 GiB. It is a real perturbation of the output: measured directly, the int8 file's next-token distribution differs from the fp32-cache file's by KL 0.013–0.037 on average (coarsened to the reference's top 64 tokens), and the top token differs on about 8–11% of positions, roughly a tenth of the divergence the 4-bit weights already bring. It showed no drift: each cell's mean divergence from the fp32 model moved by −0.020 to +0.028 (both directions), the 144 paired needle questions with valid state (LFM excluded) split 7 found only with int8 and 4 only with fp32, and on the app questions the averages improved while some individual prompts got worse. Treat this as a provisional recommendation: the intervals reflect the sampled 128-token spans of three books (one at 32k for some cells), with no preset loss margin, so they do not establish equivalence. Confirm through the app's own runner, at long contexts, before shipping.

GPU: the int8 cache cannot be used; fp16 can. In ExecuTorch 1.5.1 the int8 cache does not export for Vulkan, and Gemma 3 and LFM2.5 do not run on Vulkan at all. Vulkan's fp16 mode (force_fp16: floating-point tensors inside the Vulkan delegate, the KV cache among them, kept in fp16; the quantized weights unchanged) worked on Llama-3.2-1B at 2k: 1.21× faster decoding, 1.26× faster prefill, 0.67 GiB less GPU driver memory, and a mean coarsened KL of 0.0013 between the two files' outputs. The phone dropped out of its device-cloud session before the rest of the GPU pass ran, so this rests on one model at one window.

  • Files. Llama-3.2-1B-Instruct, LFM2.5-1.2B-Instruct, Qwen3-1.7B and Gemma-3-1B-it, each exported with ExecuPack's recipe (4-bit GPTQ weights in groups of 32, int8 dynamic activations, int8 embeddings) at 2k, 8k and 32k windows. One GPTQ solve per model, so the two files of a pair differ only in the cache. CPU files use XNNPACK; GPU files use Vulkan.
  • Phone. A Snapdragon SM8975 reference phone (Android 17, 8 cores, 11.5 GB) in Qualcomm Device Cloud. CPU files ran on the executorch-android 1.5.1 library with 7 threads, as the app does; GPU files on executorch-android-vulkan 1.5.1, because the plain library has no Vulkan backend.
  • Long text. Three PG-19 test-set books (10321, 10356, 10762), 32,500 tokens each inside the model's chat template, with nine RULER-style needles. At 1.9k, 7.9k and 32.5k tokens the phone scores 128 teacher-forced next-token predictions against the fp32 Hugging Face model. Llama and Qwen at 32k on CPU ran one book (time); the GPU pass planned the same.
  • Short chats. The 141 held-out app questions from the earlier GPTQ/AWQ experiments: first-token divergence under the app prompt, and divergence along the fp32 model's replies (every third question, 47 replies).

Every model, window and depth, fp32-cache file against int8-cache file. The int8 cache is ExecuTorch's quantize_kv_cache: keys and values stored as int8 with a scale and zero point per token and head, attention computed by its int8 kernel (which also rounds the query to int8).

Each generated token reads the whole cache, so a cache a quarter the size pays off more the longer the chat. At 1.9k tokens the gain ranges from none (LFM2.5's 32k file, which attends in only 6 of its 16 layers) to 2.8× (Qwen); at 7.9k it is 1.7–3.8×; at 32.5k, 2.5–3.3×, and 17× for Qwen, whose fp32-cache file peaked at 8.2 GiB resident on an 11.5 GB phone (memory pressure is the likely cause; the harness did not record swap or reclaim). Prefill changes less. The columns group whole chunks by the position they start at, and the first group includes each file's first call after loading, so read them as rough.

At the same 1.9k tokens, a file exported with a larger window usually decodes slower: with the fp32 cache, Llama 40 tok/s in the 2k file against 25–26 in the 8k and 32k files, LFM 66 against 38–40, Gemma 48 against 35–36. Qwen is the exception with the int8 cache (27, 30, 36 tok/s). At the same positions the files' outputs are identical across windows, so the window costs speed and memory, not quality. The smallest window that covers a use case matters as much as the cache type.

Resident memory of the benchmark process, read from /proc, in MiB. The cache is allocated in full at load, so the saving is there from the first token.

Each point is the change in mean divergence from the fp32 Hugging Face model when the int8 cache replaces the fp32 cache: KL(HF ‖ int8 file) minus KL(HF ‖ fp32 file), paired position by position, with a block bootstrap (16 neighbouring positions per block). It is not the divergence between the two files' outputs, and opposite movements can cancel; the direct comparison is in the re-run section below, and it is larger (KL 0.013–0.037). The absolute divergence (0.15–0.33) comes from the quantized model; the cache moves it by hundredths. The largest increase is Llama at 32.5k, measured on a single book and so descriptive only (+0.028, perplexity 45.7 → 48.5, agreement with the fp32 model's top token 63% → 60%); there the int8 cache found all 9 needles to the fp32 cache's 7. The intervals resample 16-position blocks within the sampled spans, not whole books, so they describe these spans rather than PG-19 at large.

Excluding LFM (below), the two caches gave the same outcome on 133 of 144 paired needle questions; 7 were found only with int8, 4 only with fp32. Both caches fail many of the same long-range needles: Gemma finds 4–5 of 27 at 32k and Qwen 4–5 of 9, where the fp32 Hugging Face model finds 12 and 7; this study does not isolate why. LFM's needles here were answered after rewinding the cache, which does not restore LFM2's convolution state, so its rows are left out of the totals; the re-run below answered its 2k and 8k needles from a fresh model and full prefix and got exactly the same outcomes (12 of 12, 21 of 21, both caches), so the rewind did not change them there (its 32k row was not re-run).

On the app questions, the average first-token divergence fell for every model (significantly for Llama, LFM and Qwen), but not every prompt improved: rows that got worse by more than 0.1 KL were 0 for Llama, 9 for LFM, 18 for Qwen and 44 for Gemma (against 67, 23, 23 and 54 that improved). Qwen agreed with the fp32 model's first token on 120 of 141 questions with the int8 cache against 124 with fp32, and its worst question went from 4.5 to 13.4 KL. Along the fp32 replies no model moved significantly. An earlier x86 run with a different Qwen solve had shown int8 +0.82 worse on this held-out metric; it is dominated by a few uncertain questions and is not a stable signal in either direction.

The 2k and 8k CPU pairs of all four models, run again on a second phone of the same model (QDC device unit-10b9a2, SM8975), with a harness that stores each file's log-probabilities on the reference's 64 tokens, so the two caches can be compared with each other and not only with the fp32 model. LFM2's needles were answered from a fresh model fed the full prefix. Every divergence value reproduced exactly on the second phone (the computation is deterministic), and decode speeds matched the first phone within about 5%, except Qwen at 2k, which ran faster on the second phone for both caches (17.9 and 35.5 against 14.1 and 27.0 tok/s), with a similar ratio (1.98× against 1.91×).

The plain executorch-android 1.5.1 library has no Vulkan backend (Backend VulkanBackend is not registered); executorch-android-vulkan 1.5.1 has, with the same Java API, and runs these files. What could be built:

  • int8 cache: does not export for Vulkan. Vulkan has no quantized attention, and lowering the int8 cache's per-token quantization fails on a data-dependent shape check (GuardOnDataDependentSymNode in FuseBatchNormPass).
  • fp16: Vulkan's force_fp16 stores and computes the delegate's floating-point tensors in fp16, the KV cache included; the 4-bit and 8-bit quantized weights stay as they are. This is the only reduced-precision cache on the GPU in 1.5.1, so the GPU pair is fp32 against fp16. Unlike the CPU pair, it changes the precision of the floating-point computation as well as the cache.
  • Models: Gemma 3 failed in this export recipe: its sliding-window attention crashes the Vulkan partitioner (IndexError in find_causal_sdpa_patterns). LFM2.5 was not attempted: the pipeline excludes it from Vulkan (no kernel for its short convolution, found under ExecuTorch 1.4.0). Llama exported at every window; Qwen at 2k and 8k, while its 32k fp32 export was killed for memory on the 52 GB build machine.
  • 4-bit cache: not available on any backend in ExecuTorch 1.5.1.

Measured before the phone dropped out: Llama-3.2-1B at 2k, three books, both caches.

On the GPU, one run per cache, Llama's 2k file prefilled at 851 tok/s with fp32 and 1,069 with fp16, and decoded at 47.0 and 57.1 tok/s, against 335 and 40 tok/s for the CPU's fp32-cache file of the same weights.

GPU files keep their buffers in the GPU driver's memory, which is not in a process's resident memory; the table adds the Adreno driver's per-process peak (/sys/class/kgsl/kgsl/proc/<pid>/kernel_max).

Directly, KL(fp32 file ‖ fp16 file) averaged 0.0013 over 384 positions (worst 0.037). It is coarsened: it compares the two files on the Hugging Face model's top 64 tokens plus one bucket for the rest, which holds about 28% of the probability on average, so differences inside that bucket are not seen. The change in mean divergence from the fp32 Hugging Face model was −0.0004 (interval −0.0046 to +0.0031); perplexity was 47.64 with fp32 and 47.65 with fp16; both found all 12 needles.

OpenAI Codex reviewed the CPU study read-only: the harness, the reference, the statistics and every claim in an earlier draft of this page. It found no off-by-one in the teacher forcing and judged that draft's verdict unsupported. This version addresses each point:

  • The KL claim. The draft said the int8 cache changes the output distribution by at most 0.03 KL. What was measured is the change in each file's divergence from the fp32 model, which does not bound the divergence between the two files. Now worded as such; a CPU re-run on a second phone recorded the per-position log-probabilities a direct comparison needs, and the page now reports that comparison (KL 0.013–0.037).
  • LFM needles. Rewinding the cache does not restore LFM2's convolution state. Re-run from a fresh model and full prefix at 2k and 8k: same outcomes; the 32k row stays out of the totals.
  • Intervals. Single-position bootstrap over correlated positions was too narrow. Now block bootstrap (books), by reply (replies) and by question (held-out); single-book cells marked as descriptive; no claim of equivalence.
  • Overstated wording. The draft said the int8 cache was never worse on the app questions, called Gemma's needle successes misses, attributed the misses to the 4-bit weights, gave inaccurate speed ranges, and called Qwen at 32k usable despite a 15-minute prefill. All corrected; per-prompt regressions and paired needle outcomes are now reported.
  • Units and charts. Memory in MiB; the speed chart's axis follows the data; prefill columns labelled by chunk start.

Not addressed, by design or time: timing repetitions under controlled temperature, and validation through the app's own runner at long contexts.

  • Harness. StudyBench calls the program's forward() through the Android library's Module API: prefill in chunks of get_max_seq_len − 1 tokens (2,047; 511 for Gemma), then single-token decode steps whose input is always the book's true next token. Each forward() is timed, including tensor creation and copying the logits out, not the scoring that follows. Model files reached the phone with sha256 checks.
  • Divergence. KL(fp32 HF ‖ file) over the reference's top 64 tokens plus one bucket for the rest, as in the earlier experiments. The GPU pass also stored each file's log-probabilities on those 64 tokens, so its two files can be compared directly.
  • Intervals. Block bootstrap over runs of 16 neighbouring positions for the books; by reply for the replies; by question for the held-out first tokens. 95% percentile intervals, no correction for the number of comparisons; single-book cells are descriptive.
  • References. The book reference is Hugging Face fp32 on a GPU with TF32 off, on the same token IDs and model revisions as the exports. The app reference is Hugging Face fp32 on the CPU (the earlier experiments' awq_compare reference; Gemma's made the same way for this study).
  • Gemma 3. ExecuTorch 1.5.1 has no CPU path for it; this study adds one (separate RoPE for the sliding layers, ring caches, 512-token prefill chunks). The ExecuTorch model matched Hugging Face at KL ~1e-9 before quantization, and the exported 2k file without quantized linears at KL 0.0003.

fp16 on the CPU and 4-bit caches. A 16-bit cache on the CPU needs an fp16 model, and the 1.5.1 Android library has no XNNPACK kernel for 4-bit weights with fp16 activations: every CPU fp16 file failed to load (xnn_status_unsupported_hardware), though fp16 itself runs on this phone. ExecuTorch 1.5.1 has no 4-bit KV cache on any backend.

Speed. No repeated runs of the same file; runs of a pair were not adjacent in time and started at different temperatures (logged, not controlled); downloads overlapped some CPU runs, notably LFM's 32k int8 run. The harness's fp32 decode on Qwen 2k was close to the app's own runner (14.1 vs 15.9 tok/s, different prompt and warm-up); with int8 the runner was faster (36.6 vs 27.0). Absolute speeds are approximate, and the ratios carry the same run-order and temperature caveats; the large effects (2–4× at depth) are well beyond them, the small ones (under ~1.15×) are not.

Scope. One phone, one long session, three books (one at 32k for some cells), teacher-forced spans of 128 tokens and short needle answers. This measures how the cache changes the model's predictions, not end-to-end chat quality.

Before shipping the int8 cache. sizing.kv_bytes_per_token must count it (1 byte per value plus a scale and zero point per token and head, about 27% of fp32) for fits_phone_budget and the README; no work path may contain "int8", which ExecuTorch 1.5.1 mistakes for an int8 weight-only checkpoint; and the cache stays off GPU builds.
